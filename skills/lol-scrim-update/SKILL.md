# LOL 内战数据更新

## 先定位数据和网站

找到当前网站的 `data.json`、`index.html`、Git remote 与已有锐评。优先使用用户已指定的仓库；未指定项目时参考 [当前演播室](references/current-project.md)。找不到本地项目时搜索工作区或克隆该仓库，不硬编码旧日期、游戏账号、安装路径、固定十人或四场。阅读 [接口与数据口径](references/data-and-api.md)；要生成评语时阅读 [评选与发布](references/review-and-publish.md)。

用户要整理好友灵排时走 [好友灵排与收集模式](references/flex-collection.md)，使用独立 `flex/` 数据集；不要将下面的十人内战评奖和合并规则套到仅含友方好友的灵排数据。

用户要采集其他好友各自的战绩并合并时，走该参考中的“多账号好友全量采集”，先确定具体账号名单。使用独立 `friends/` 数据集，允许本人不在场与仅一位名单选手参战的灵排；按比赛去重、按选手各自队伍统计胜负，不把这些比赛当作本人参加。

## 读取真实比赛

1. 客户端已登录时，运行 `scripts/collect.py --output <网站目录之外的私有文件> --history-count 60 --max-games 20`，只读查询本机 LCU。明确指定比赛可加 `--game-ids ID1,ID2`。
2. 需要 SGP 补全位置和详细时间线时，加 `--allow-sgp`。脚本从本机 Akari 配置匹配比赛大区，访问配置内的腾讯 HTTPS 服务器；平台无法推断时传 `--platform HN1` 等实际大区。说明将使用当前登录令牌向对应服务器查询战绩。已有授权足够时继续；工具若要求新的目的地授权，遵守其限制。旧会话中限定四次查询的授权不扩展为无限查询授权。
3. 默认只选择 `CUSTOM_GAME`、十名参与者的比赛，核对竞技征召、日期、对局 ID、时长和双方阵容。用户指定其他模式时调整选取规则并说明。不启动新对局、不修改 BP，不查询无关玩家的全部历史。
4. 客户端未就绪时使用已有私有导出、用户提供的比赛 JSON，或启动用户已授权的客户端。不能读取就说明缺少什么，不伪造新比赛，不索要或保存登录令牌。掌上英雄联盟不是已验证的通用采集接口。

## 合并、点评、构建

```text
python scripts/merge.py --site <网站根目录> --input <私有比赛导出> [--sgp <旧格式SGP导出>] [--roles <人工位置映射JSON>]
python scripts/report.py --site <网站根目录> [--games 1,2,3,4] --output <私有统计报告>
python scripts/merge.py --site <网站根目录> --awards <审核后的锐评JSON>
python scripts/build.py --site <网站根目录> [--html <分享用单文件HTML>] [--download-icons]
```

- 以 `platformId:gameId` 去重，保留稳定比赛编号和原来的点评。同一比赛的新数据只补强时间线、可信位置，不以缺失信息覆盖已有完整数据。原始导出放在网站之外。
- 灵排名单按用户确认维护，应用仓库根目录 `roster-policy.json` 的排除规则；移除玩家时同步删除名单、个人行、仅含已移除成员的比赛、来源记录，重建日期/采集计数并重算评分与锐评；保留真实完整五人分母与其他选手对位数据。未来 merge/review 自动过滤，build 拒绝含已排除玩家的数据。位置优先人工核实，其次 SGP `teamPosition`；无法确认写 `UNKNOWN`。没有真实 10/15 分钟帧或唯一同位置对手时，对位差为 null；不拿赛后金币或最后一帧冒充对线数据。
- 报告分别生成全部、胜局、败局及位置统计。先复核数据，再为每局写四个奖项：MVP、SVP、胜方最坑、败方最坑。总评必须注明具体比赛集合与赢/败局范围。评语采用原创、搞笑、狠辣的游戏表现吐槽，每条附证据、理由和争议候选；不套用上一场的点评。
- 合并支持 `awards.matches`（比赛 key 或稳定编号）与 `awards.collections`（精确比赛集合）。没有完成点评的新增比赛显示“锐评待生成”，不要用自动候选冒充已分析结论。
- 保留跨日期筛选、任意场次选择、A/B 两组比较；蓝红只代表该局地图侧，不当成永久队伍。比赛样本不足时标出场数。
- 内战页面有 `#radar` 对位雷达时，保留 `radar.js`、`radar.css` 与相关入口。八轴按位置配置：共同轴为伤害占比、经济、参与击杀、参团率、生存、伤害；上单/打野另用每死承伤和补刀，中单/射手另用伤转和补刀，辅助另用每死承伤和视野。伤转为英雄伤害/金币，客户端视野得分的口径须明确。每个位置独立权重合计 100%，使用同位置百分位加权得到位置表现分，并展示单项权重与贡献。注明权重来源，不把本站配置冒充参考视频原公式。轮廓使用同位置历史百分位，轴旁保留实值；合并时分别平均单局实值与单局百分位。缺项断线且不生成完整分数，展示覆盖。新增数据后动态网页自行重算；静态 `radar-samples/` 是带日期快照，另行生成才更新。网页模块的 `SCRIM_RADAR.model` 可导出同一图表模型供标准绘图库生成分享图。

- 好友灵排有 `#radar` 时，保留 `friend-radar.js`/CSS 及共用 `radar.js`/CSS。单人图按玩家身份和已确认位置合并；双人图固定同一个位置，分别计算每人的所选出场，不要求两人同时参与。本人及用户确认的好友进入雷达与参照池，未知位置不混入已确认位置。沿用该位置独立指标与权重；固定本数据集全历史同位置名单选手基准，对日期/自选比赛/包含选手/组队筛选后的个人实值与单局百分位分别求均值，显示每人的场数、胜率、有效样本、权重贡献、原始差值与 SVG 下载。支持 A/B 交换、无记录/缺指标/仅一位同位置好友，离线 HTML 嵌入模块。更新两套灵排时保持各自数据隔离；新增数据后动态重算，不再采集即可生成已有战绩的雷达。

## 验证和交付

核对新比赛数、重复数、双方击杀与选手合计、BP 分母、数据覆盖和锐评范围。验证重复导入不会增加场数、未知位置不崩溃、未满 15 分钟显示空值；检查桌面与手机布局、选择场次、A/B 比较、逐局锐评和离线 HTML。只在新变更需要时重测。

按用户意图更新仓库与公开站点，不默认套用旧仓库或旧授权。发布前检查实际 `git diff` 和暂存文件，不发布原始战绩、PUUID、认证头、令牌或本机连接信息。GitHub Pages 发布后，用无需登录的访问验证页面和数据，再交付公开链接、仓库链接、新增比赛列表及缺失项。没有完成上线就明确说明实际状态。
